Execution Context

Everything in JavaScript happens inside an Execution Context, when you run the javascript code this Execution Context will create.

Think Execution Context as a box
Inside this box we have 2 parts:

1. Memory Phase (Creation Phase)

Variables and functions are stored as key-value pairs

Example: var a = 10;

Stored as:
 a → undefined

Example: function fn() {}

Stored as:
fn → function definition

2. Code Phase (Execution Phase or Thread of Execution)

Code runs line by line
Values are assigned here 

javascript is the synchorous and single threaded language, Thread means tasks that is executing

JavaScript Nature
JavaScript is single-threaded : Executes one task at a time
JavaScript is synchronous : Executes code line by line in order
(It supports async — we will learn later)
Simple JS program
 
var a = 2;                             
function squareRoot(num){
 var ans = num * num;
 return ans;
}

var square2 = squareRoot(a);
var square4 = squareRoot(4);

Let see how it works? 

As soon as the above code getting runs,
GEC - Global execution context will create. think of it like a box will create, inside that as discussed earlier

How it works?

GEC (Global Execution Context)
Memory Phase Code Execution Phase
var a : undefined a = 2 (value assigned)
function squareRoot() -> function declaration (whole function stored) -
var square2 : undefined squareRoot(a) is called -> a new FEC is created and pushed onto the call stack
Function Execution Context 1 - squareRoot(2)
Memory Phase Code Execution Phase
num : 2 (arg)
ans : undefined		 code executes line by line
ans : 4 (updated) var ans = num * num; -> 2*2 = 4

square2 = 4 (GEC memory phase updated with the returned value)
var square4 : undefined squareRoot(4) is called -> a new FEC is created and pushed onto the call stack
Function Execution Context 2 - squareRoot(4)
Memory Phase Code Execution Phase
num : 4 (arg)
ans : undefined		 code executes line by line
ans : 16 (updated) var ans = num * num; -> 4*4 = 16
return ans; -> 16 is returned to the caller

FEC 2 is popped off the stack (deleted) once return executes. Control jumps back to GEC.

square4 = 16 (GEC memory phase updated with the returned value)

Once the entire program finishes executing, GEC is popped off the call stack and deleted.

📦 CALL STACK

Call Stack is a single vertical stack (box) that manages execution contexts.
At the bottom of the stack, Global Execution Context (GEC) is pushed first.

Whenever a function is invoked:
- A new Function Execution Context (FEC) is created
- It is pushed on top of the Call Stack
- The function executes its code line by line
- Once the function's last line finishes (whether or not it has a return statement):
    - If there is a return, the value travels back down to the caller
    - That FEC is popped (removed) from the stack
- Control goes back to exactly where the caller left off
- This process continues for every function call

⚠️ Important Points
- Only one call stack exists
- Multiple execution contexts (FECs) can exist inside the same stack at once — 
  stacked on top of each other, not side by side
- A paused FEC (caller waiting on a callee) is NOT deleted — it stays frozen 
  in place until everything above it finishes and pops
- GEC stays in the stack until the entire program finishes
- Popping always happens top to bottom → this is LIFO (Last In, First Out)
    Call stack also knows as below fancy names:
  1. Execution Context stack
  2. Program stack
  3. Control stack
  4. Runtime stack
  5. Machine stack

Code being traced:

function A() {
  B();
}
function B() {
  C();
}
function C() {
  console.log("Hello");
}
A();
Step 1: Program starts
Global (GEC)
Step 2: A() called
A ← top (active)
Global (GEC)

A's FEC pushed. Line 2 of A (B();) is about to run.

Step 3: B() called (inside A)
B ← top (active)
A (paused)
Global (GEC)

A is paused, not deleted — it's waiting for B to finish and hand control back.

Step 4: C() called (inside B)
C ← top (active)
B (paused)
A (paused)
Global (GEC)

Stack is now 4 deep. All 3 FECs coexist — this is the "multiple execution contexts in one stack" case.

Step 5: C executes console.log("Hello")
B ← top again
A (paused)
Global (GEC)

C's last line finished → C popped. Control returns to B, exactly where B left off (right after the C(); call).

Step 6: Control returns to B — nothing left in B
A ← top again
Global (GEC)

B had only one line (C();), already done → B popped. Control returns to A.

Step 7: Control returns to A — nothing left in A
Global (GEC)

A had only one line (B();), already done → A popped.

Step 8: Program finishes
Empty stack

No more code. GEC popped. Stack empty — this is LIFO: C (last in) was the first out, then B, then A.

1️⃣ Scope — what is it?

Scope = a variable எங்க இருந்து access பண்ண முடியும் அப்படிற area.

Scope-ன்னா ஒரு variable-ஐ code-ல எந்த இடத்துல இருந்து access பண்ண முடியும்ங்கிற பகுதி.

🔹 Global Scope — எல்லா இடத்துலயும் access பண்ணலாம் 
var a = 20;
🔹 Local Scope (of one()) — one()-க்குள்ள மட்டும் access பண்ணலாம் 
function one() {
    var a = 10;
    ...
}
🔹 Nested Scope (of two()) — two()-க்கு one()-ஓட variables-ஐயும் access பண்ண முடியும் 
function two() {
    console.log(a); // one()'s a-ஐ access பண்ணும்
}

🌍 GLOBAL SCOPE, FUNCTION SCOPE, BLOCK SCOPE

1️⃣ Global Scope

Top level-ல் (எந்த function-க்குள்ளையும் இல்லாம) declare பண்ணப்பட்டா → Global Scope. எங்க இருந்தும் access பண்ணலாம்.

var x = 100; // global scope
console.log(x); // 100 — access from anywhere ✅

2️⃣ Function Scope

ஒரு function-க்குள்ள declare பண்ணப்பட்டா → Function Scope. அந்த function-க்குள்ள மட்டும் access பண்ணலாம், வெளிய இருந்து access பண்ண முடியாது.

Global 
function test(){
    var y = 20; // function scope — only inside test()
    console.log(y); // 20 ✅
}
test();
console.log(y); // ❌ ReferenceError: y is not defined

Your understanding here is correct — var, let, and const ALL respect function scope.

3️⃣ Block Scope

எந்த { } curly braces pair-உம் ஒரு block தான் — if, for, while, switch, மட்டும் இல்ல, keyword இல்லாம தனியா { } வெச்சாலும் அது block தான்.

Global 
{
    let z = 30; // block scope
    console.log(z); // 30 ✅
}
console.log(z); // ❌ ReferenceError: z is not defined

👉 keyword எதும் இல்லாம தனியா { } வெச்சாலும் அது block தான் — if/for மட்டும் இல்ல.

⚠️ The catch: var does NOT respect block scope

if (true) {
    var a = 10; // var IGNORES the block
}
console.log(a); // 10 ✅ — 'a' leaked out of the block
if (true) {
    let b = 10; // let RESPECTS the block
}
console.log(b); // ❌ ReferenceError — 'b' stayed inside the block

👉 var block-ஐ respect பண்ணாது — block-க்குள்ள declare பண்ணாலும், அது function scope (அல்லது function இல்லாட்டி global) போய் சேரும். let/const மட்டும் தான் block-க்குள்ளயே stay ஆகும்.

2️⃣ Lexical Environment — what is it?

Lexical Environment = Local memory (இந்த function-க்குள்ள இருக்கிற variables) + Outer reference (parent-க்கு ஒரு pointer)

Lexical Environment-ன்னா அந்த function-ஓட own memory + அது யார் அப்பாடி (parent) இருக்கு அப்படிற ஒரு reference/pointer.

⚠️ மிக முக்கியம்: "Outer reference" முடிவு பண்றது — function எங்க CALL ஆச்சுங்கிறதுல இல்ல, function எங்க WRITE பண்ணப்பட்டுச்சுங்கிறதுல தான் (இதுக்குத்தான் Lexical scoping-ன்னு பேரு).

⚠️ Important: "Outer reference" is decided by where the function is WRITTEN, not where it's CALLED from. That's exactly why it's called Lexical scoping.

Function Local Memory Outer Reference (Lexical Parent)
two() (no local a) → one() (ஏன்னா two, one-க்குள்ள WRITE பண்ணப்பட்டிருக்கு — one() call பண்ணின இடம் இல்ல)
one() a = 10 → Global (ஏன்னா one, top-level-ல் WRITE பண்ணப்பட்டிருக்கு)

3️⃣ Scope Chain — how variable lookup works

Scope Chain = ஒரு variable-ஐ தேடுற process: current scope → அதுக்கு Lexical parent-ஆ இருக்கிற scope → அதுக்கு parent... இப்படியே Global வரைக்கும்.

Global: a = 20
one(): a = 10
two(): a இல்ல → Lexical parent (one()) பாக்கும் → a = 10 கிடைக்கும் → STOP இங்கயே, மேல போகாது

Step by step:

  1. two() தன் own memory-ல a-ஐ தேடும் → கிடைக்கல
  2. அதுக்கு அப்புறம் two()-ஓட Lexical parent-ஐ பாக்கும் — அது one() (call பண்ணின இடம் இல்ல!) → a = 10 கிடைக்கும்
  3. கிடைச்சதும் search stop ஆயிரும். Global-ல a = 20 இருந்தாலும், அது வரைக்கும் போகவே போகாது.

👉 இதனால தான் output 10 வரும், 20 இல்ல.

🔹 var — Function Scoped

var is stored in the window object with undefined before it's initialized — so accessing it early just gives undefined, never an error.

var, window object-ல undefined-ஆ முதல்ல store ஆகும் — அதனால அதை initialize ஆகுறதுக்கு முன்னாடியே access பண்ணா, error வராம undefined தான் வரும்.

if (true) {
  var a = 10;
}
console.log(a); // 10 ✅
// var IGNORES block { } — it leaks out to function/global scope
var a = 10;
console.log(window.a); // 10 ✅
// proof that var attaches itself to window

🔹 let & const — Block Scoped + TDZ

let and const ARE hoisted (memory is reserved), but they are not initialized — so accessing them before their declaration line throws an error. This gap between "hoisted" and "initialized" is called the Temporal Dead Zone (TDZ).

let, const-உம் hoist ஆகும் (memory reserve ஆகும்), ஆனா initialize ஆகாது — அதனால அதை declare பண்ணுற லைன்-க்கு முன்னாடியே access பண்ணா error வரும். இந்த "hoisted ஆனா initialize ஆகாத" gap-க்கு பேரு Temporal Dead Zone (TDZ).

if (true) {
  let a = 10;
}
console.log(a); // ❌ ReferenceError: a is not defined
// let RESPECTS the block { } — 'a' doesn't exist outside it at all
let b = 20;
console.log(window.b); // undefined ❌
// b exists, but NOT on window — that's why window.b shows undefined,
// NOT because b itself is undefined

⚠️ TDZ — Step by Step (the tricky one)

console.log(a);
console.log(b);
let a = 9;

  • a → reserved, but in TDZ (not usable yet)
  • b → reserved, but in TDZ (not usable yet)
GEC Execution Phase (line by line):
  1. console.log(a) → a is still in TDZ → ❌ ReferenceError: Cannot access 'a' before initialization
  2. Execution STOPS immediately. Line 2 (console.log(b)) never even runs.

👉 முக்கியம்: இது "எது first-ஆ error தரும்"-ன்னு JS தேர்ந்தெடுக்கல. Top-to-bottom-ஆ படிக்கும், a தான் முதல் TDZ variable-ஆ இருக்கு, அதனால அதுல throw ஆகி, அப்புறமே stop ஆகிடும். b-ஓட லைன் run-ஆவே ஆகாது.

🔍 A different case — accessing an undeclared variable

// ❌ ReferenceError: b is not defined

Error message What it actually means
Cannot access 'a' before initialization a EXISTS (hoisted), but you're in its TDZ — too early
b is not defined b DOESN'T EXIST in this scope at all — never declared

GEC Memory Phase (hoisting — happens for ALL declarations, top to bottom order doesn't matter):
  • c → var → auto-initialized to undefined (usable immediately)
  • a → let → reserved, in TDZ
  • b → const → reserved, in TDZ
Execution:
  1. console.log(c) → c is var, already undefined in memory → prints undefined ✅ (no error)
  2. console.log(a) → a still in TDZ → ❌ throws immediately, execution stops here

👉 c மட்டும் var-ஆ இருக்குறதால, அது hoisting-ல் நேரடியா undefined கிடைக்கும் — error இல்ல. ஆனா a-ஓட லைன் வந்ததும், TDZ-ல இருக்குறதால error throw ஆகிடும்.

❌ SyntaxError case

// SyntaxError: Identifier 'a' has already been declared

Same variable name declared twice in the same scope using let/const → this is caught before the code even runs (it's a parse-time error, not a runtime error).

ஒரே scope-ல ஒரே பேர் let/const-ல ரெண்டு தடவை declare பண்ணா → code run ஆகுறதுக்கு முன்னாடியே இந்த error பிடிபடும் (இது parse-time error, runtime இல்ல).

❌ TypeError case

a = 0;
// TypeError: Assignment to constant variable.

const creates a binding that cannot be reassigned after initialization. Note: this is different from "immutable" — if a were an object, you could still change its *properties*, just not reassign a itself.

const-ஓட value-ஐ initialize பண்ணதுக்கு அப்புறம் மாத்த முடியாது. ஆனா இது "immutable"-க்கு வேற — a ஒரு object-ஆ இருந்தா, அதுக்குள்ள properties மாத்தலாம், a-வையே reassign பண்ண முடியாது.

✅ Exceptional case — var CAN redeclare

// var allows redeclaring the same name — last assignment wins

This works with zero errors because var doesn't check for existing declarations the way let/const do — each var a just re-points to the same function-scoped memory slot.

🎯 Why ES6 introduced let/const — and why we prefer them

Your question at the end — "why we neglect var and use let/const" — here's the direct answer:

No block scope — leaks out of if, for, etc., causing accidental bugs Block scoped — a variable inside { } stays inside { }
Silent redeclaration — accidentally declaring the same variable twice overwrites it with no warning SyntaxError immediately catches accidental duplicate names — bugs caught early, not silently

🌑 VARIABLE SHADOWING

📌 What is it?

Variable Shadowing = when a variable declared in an inner scope has the SAME NAME as one in an outer scope, the inner one "hides" (shadows) the outer one — completely, for that entire inner scope, from the very start.

Variable Shadowing-ன்னா, inner scope-ல ஒரு variable, outer scope-ல இருக்கிற அதே பேர் வெச்சு declare பண்ணப்பட்டா, அந்த inner variable, outer variable-ஐ முழுசா "மறைச்சிடும்" (shadow பண்ணிடும்) — அந்த inner scope முழுக்கவும், ஆரம்பம் இருந்தே.

⚠️ Golden Rule: "If a variable with that name exists in the current scope, JavaScript will NEVER look outside — even if the current scope's version is still undefined or in TDZ."

⚠️ முக்கிய rule: "அந்த பேர்ல ஒரு variable current scope-லயே இருந்தா, JS ஒருபோதும் வெளிய தேடாது — current scope-ஓட version இன்னும் undefined-ஆ அல்லது TDZ-ல இருந்தாலும் சரி."

1️⃣ Your Example — var shadowing var

console.log(a);
var a = 10;

function test() {
    console.log(a);
    var a = 20;
}
test();
GEC Memory Phase: a → undefined, test → function
GEC Execution:
  1. console.log(a) → global a is still undefined at this point → prints undefined
  2. a = 10 → global a now 10
  3. test() called → new FEC created
test()'s Memory Phase: a → undefined (test() has its OWN local a, thanks to var a = 20 inside it)
test()'s Execution:
  1. console.log(a) → JS checks CURRENT scope first → local a exists (even though it's still undefined right now) → STOPS here, never checks global → prints undefined
  2. a = 20 → local a now 20 (but nothing logs it after this)

Output: undefined then undefined

👉 Global-ல a = 10 இருந்தாலும், அது shadow ஆகி hide ஆகிடுச்சு — test()-க்குள்ள, JS local a-வை பாத்ததும், global-ஐ ஒருபோதும் பாக்கவே இல்ல.

2️⃣ Legal Shadowing — let shadowing let (each block gets its own copy)

let x = "outer";

if (true) {
    let x = "inner"; // shadows outer x, ONLY inside this block
    console.log(x); // "inner"
}
console.log(x); // "outer" — unaffected, back to original
This is legal shadowing — let creates a fresh block-scoped copy each time, and the outer x is completely safe once you exit the block. This is actually a GOOD, common, and safe pattern (e.g. loop variables, if-blocks).

இது legal shadowing — let, ஒவ்வொரு block-க்கும் ஒரு புது copy create பண்ணும், block முடிஞ்சதும் outer x பாதிக்காம சேஃப்-ஆ இருக்கும். இது நல்ல, சரியான, safe pattern (loop variables, if-blocks-ல சகஜமா use ஆகும்).

3️⃣ Illegal Shadowing — mixing let/var incorrectly

let y = "outer";

if (true) {
    var y = "inner"; // ❌ SyntaxError: Identifier 'y' has already been declared
}
This is illegal shadowing. var ignores block scope — so it tries to declare y in the SAME scope where the outer let y already lives, and JS won't allow two declarations of the same name in one scope when let/const is involved. This throws immediately, before any code runs.

இது illegal shadowing. var, block-ஐ ignore பண்ணிடுறதால், outer let y இருக்குற அதே scope-லயே y-ஐ declare பண்ண try பண்றது — ஒரே scope-ல ரெண்டு declaration, அதுவும் let/const involve ஆனா, JS அனுமதிக்காது. Code run ஆகுறதுக்கு முன்னாடியே இது throw ஆகிடும்.

Reverse case (this one IS allowed):

var z = "outer";

if (true) {
    let z = "inner"; // ✅ totally fine
    console.log(z); // "inner"
}
console.log(z); // "outer"
Here let z is genuinely block-scoped and separate from outer var z (which lives in function/global scope) — no collision, so this works fine.

4️⃣ Function Parameter Shadowing

let msg = "global message";

function greet(msg) {
    console.log(msg); // uses the PARAMETER, not the outer variable
}
greet("hello"); // "hello"
console.log(msg); // "global message" — untouched

👉 Function parameter-உம் ஒரு தனி local variable தான் — outer msg-ஐ shadow பண்ணிடும், function-க்குள்ள.

Step 2: JavaScript asks itself a question

outer() has finished. Should its Lexical Environment (including name) be deleted?

And realizes: "This function still needs `name`. If I delete it, `greet()` won't work later."

⚠️ One refinement to your third question

Your original phrasing — "can it live after the outer function ends?" — is true for the most common, most visible closure pattern (return a function, store it, call it later). But it slightly undersells when a closure actually forms. A closure exists the moment the inner function is defined, not the moment the outer function finishes. The "outer function ends" part is just what makes it obvious — because that's when you'd normally expect the variable to be gone, and it isn't.

Closure, inner function define ஆகும் நேரமே create ஆகிடும் — outer function முடியும் வரைக்கும் காத்திருக்கல. Outer function முடிஞ்சதும் மட்டும் நாம அதை "கண்ணுக்கு தெரியற மாதிரி" பாக்கறோம், அவ்வளவுதான்.

✅ Example 1 — Closure (matches all three questions)

function outer() {
    let name = "Kesava";
    function inner() {
        console.log(name);
    }
    return inner;
}
const greet = outer();
greet();
  • Inner function? → Yes (inner)
  • Uses an outer variable? → Yes (name)
  • Accessible outside outer? → Yes — returned, stored in greet, called later
→ Closure ✅

✅ Example 2 — Closure, WITHOUT the outer function ever finishing first

function outer() {
    let name = "Kesava";
    function inner() {
        console.log(name);
    }
    inner(); // called immediately, WHILE outer() is still running
}
outer();
  • Inner function? → Yes
  • Uses an outer variable? → Yes
  • Accessible outside outer? → No — but that's not required. inner is still reading name through the closure, right now, while outer is on the call stack.
→ Still technically a closure ✅ — just an invisible one, because nothing outside outer ever needs to reach in and prove it. This is why most explanations (including your original) focus on the return-and-call-later pattern: that's the only version where the closure is provable from outside.

Nodejs is a single threaded asynchronous I/O approach, hence it is tied to a single thread. but it handles async functions with the help of this.


Core Concepts

  1. Call Stack - (Execution stack - in the browser or memory of runtime in each and every function execute based on first-in-first-out basis. if all functions get executed the call stack will be empty. This is a normal sync function and after all executed function also closed.)
  2. Callback Queue - (Here if its a async function, example we have settimeout after the function execution stack will empty and after that the settimeout is triggered so inside the stack like queue system it happen)

The event loop continues this process, ensuring that the call stack is always empty before taking the next function from the callback queue.
