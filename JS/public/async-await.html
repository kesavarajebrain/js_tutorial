JavaScript — Async & Await / Fetch API

1. What Is async/await?

async/await is modern JavaScript syntax used to work with Promises in a cleaner and more readable way. It allows asynchronous code to look similar to normal sequential JavaScript.

Before async/await, we commonly handled asynchronous operations using callbacks and Promise .then() and .catch(). Although Promises solve many problems associated with nested callbacks, long Promise chains can still become difficult to read.

Callbacks → Promises → async/await
Basic async handling → Better chaining → Cleaner syntax

Version information: Promises — ES2015 (ES6). async/await — ES2017 (ES8).

2. What Does async Do?

When we add async before a function, that function always returns a Promise.

Normal Function
function getName() {
    return "John";
}

const result = getName();
console.log(result);
Output 
John
Returns a normal string.
Async Function
async function getName() {
    return "John";
}

const result = getName();
console.log(result);
Output (conceptually) 
Promise { fulfilled: "John" }
Returns a Promise fulfilled with the string.

Conceptually, returning a normal value from an async function behaves similarly to: 

function getName() {
    return Promise.resolve("John");
}
Async Function Return Behaviour
Code inside async function Returned Promise
return "John" Fulfilled with "John"
return 100 Fulfilled with 100
No return statement Fulfilled with undefined
throw new Error("Failed") Rejected with that error
return anotherPromise Adopts that Promise's eventual outcome
Important: An async function does not necessarily execute asynchronously from its first statement. It starts executing immediately and runs synchronously until it reaches an await or finishes.

3. What Does await Do?

await has two important responsibilities:

1. Gets the Fulfillment Value
It provides the actual fulfilled value of a Promise instead of making us work directly with its Promise object. 
const value =
    await Promise.resolve(10);

// value = 10
2. Suspends the Async Function
Suspends the remaining execution of the current async function and resumes it later as a microtask. 
const value = await getData();

// Remaining code
// resumes later

Important: await does not block the entire JavaScript thread. Other JavaScript work can continue while the async function is suspended.

Example A: Without await
async function test() {
    const result = Promise.resolve(10);

    console.log("A");
    console.log(result);
}

console.log("Start");
test();
console.log("End");
Output 
Start
A
Promise { <fulfilled>: 10 }
End

result contains a Promise object. Since there is no await, the function is not suspended and its statements execute immediately.

Example B: With await
async function test() {
    const result = await Promise.resolve(10);

    console.log("A");
    console.log(result);
}

console.log("Start");
test();
console.log("End");
Output 
Start
End
A
10

Even though the Promise is already fulfilled, await suspends the function's continuation. The outside synchronous code executes, then the async function resumes as a microtask.

Without await vs With await
Without await With await
Promise object is received. Fulfillment value is received.
Function continues immediately. Current async function's continuation is suspended.
Subsequent statements execute normally. Subsequent statements execute after resumption.
No await continuation is scheduled. Continuation resumes as a microtask.

8. Nested Async Functions

Different async functions can suspend independently when they encounter their own await statements. 

async function first() {
    console.log("First started");
    return 10;
}

async function second() {
    console.log("Second started");

    const value = await first();

    console.log("Second resumed:", value);
}

async function third() {
    console.log("Third started");

    await second();

    console.log("Third resumed");
}

console.log("Start");
third();
console.log("End");

Start

First started
End

Third resumed
Execution Walkthrough
  1. third() starts.
  2. It calls second().
  3. second() calls first().
  4. first() executes synchronously and returns a fulfilled Promise containing 10.
  5. second() suspends at await first().
  6. third() suspends at await second().
  7. Outside synchronous code executes End.
  8. second() resumes and completes its Promise.
  9. third() resumes afterward.
Golden Rule: If another async function awaits the Promise returned by a function that is itself suspended, the caller may also suspend until that Promise settles.

A very important distinction:

    await Promise.resolve();

    console.log("A");

        console.log("B");
    });

    console.log("C");

console.log("End");

End

C

Why?
  1. The first await suspends test().
  2. End executes.
  3. test() resumes as a microtask.
  4. A executes.
  5. Callback B is added to the Microtask Queue.
  6. C executes.
  7. Callback D is added to the Microtask Queue.
  8. E executes.
  9. The current continuation finishes.
  10. The queued callbacks execute in FIFO order: B, then D.
Remember: A currently executing callback must run to completion. A newly scheduled microtask does not interrupt it.

11. throw vs Promise.reject() vs return await Promise.reject()

These three expressions behave differently inside try/catch.

A. throw
async function test() {
    try {
        throw new Error("Failed");
    }
    catch (error) {
        console.log("Caught:", error.message);
    }

    return 100;
}

test().then(value => {
    console.log("Result:", value);
});
Output 
Caught: Failed
Result: 100

The throw occurs inside try, so its catch handles it.

B. return Promise.reject()
async function test() {
    try {
        return Promise.reject("Failed");
    }
    catch (error) {
        console.log("Inner:", error);
    }
}

test().catch(error => {
    console.log("Outer:", error);
});
Output 
Outer: Failed

The rejected Promise is returned without awaiting it. The local catch does not intercept that Promise rejection.

C. return await Promise.reject()
async function test() {
    try {
        return await Promise.reject("Failed");
    }
    catch (error) {
        console.log("Inner:", error);
    }

    return 100;
}

test().then(value => {
    console.log("Result:", value);
});
Output 
Inner: Failed
Result: 100

await exposes the rejection inside try, so the inner catch handles it.

Practical note: return await is useful when the current try/catch must handle a rejection. Otherwise, directly returning an existing Promise is often sufficient.

12. return Inside catch — Promise Recovery

async function test() {
    try {
        const employee =
            await Promise.reject("Employee API failed");

        console.log(employee);
    }
    catch (error) {
        console.log("Caught:", error);
        return "Default Employee";
    }

    console.log("Completed");
}

test().then(value => {
    console.log("Final:", value);
});
Output 
Caught: Employee API failed
Final: Default Employee

Why doesn't Completed execute? Because return exits the entire async function immediately. The returned Promise is fulfilled with "Default Employee".

This is called Error Recovery: We handle a failure and return an alternative value, allowing the async function's Promise to fulfill successfully.

13. What Does finally Do?

.finally() executes after either fulfillment or rejection. It is commonly used for cleanup activities such as hiding loading indicators. 

getEmployee()
    .then(employee => {
        console.log(employee);
    })
    .catch(error => {
        console.log(error);
    })
    .finally(() => {
        console.log("Loading completed");
    });
Important Rules
  • .finally() runs after fulfillment or rejection.
  • It normally preserves the original Promise outcome.
  • It doesn't automatically turn a rejected Promise into a fulfilled one.
  • If finally throws an error or returns a rejected Promise, the resulting chain becomes rejected with that new failure.

Modern applications depend on external systems and asynchronous operations. We use async/await to work with their results in a readable and structured way.

Practical Example: Employee Management Application

Imagine an employee dashboard. We need to fetch employee details, use the employee ID to fetch orders, and use the order ID to fetch order details.

Promise Chaining Approach
getEmployee(101)
    .then(employee => {
        return getOrders(employee.id);
    })
    .then(orders => {
        return getOrderDetails(orders[0].id);
    })
    .then(details => {
        console.log(details);
    })
    .catch(error => {
        console.log(error);

Async/Await Approach
async function loadEmployeeDashboard() {
    try {
        const employee = await getEmployee(101);
        const orders = await getOrders(employee.id);
        const details = await getOrderDetails(orders[0].id);

        console.log({
            employee,
            orders,
            details
        });
    }
    catch (error) {
        console.log("Dashboard loading failed:", error);
    }
}

Notice how easy the async/await approach is to follow. Each operation executes after the previous awaited operation provides its result.

15. Important: Does await Always Mean Sequential Execution?

No. How and when we start the Promises matters.

Sequential — Dependent Operations
const employee = await getEmployee();

const orders = await getOrders(employee.id);
getEmployee()
↓ Wait for result
getOrders(employee.id)

The second operation needs the first operation's result, so we await them sequentially.

Concurrent — Independent Operations
const [employee, department, projects] =
    await Promise.all([
        getEmployee(),
        getDepartment(),
        getProjects()
    ]);
getEmployee()
getDepartment() → Concurrent
getProjects()
↓
Await combined result

All independent operations start before we await their combined result.

Using await does not automatically make independent operations run concurrently. We must start their Promises before waiting for their combined result.

17. Final Takeaway — Why Do We Need async/await?

Modern applications depend on external systems:

Backend APIs
Databases
Authentication services
Cloud services
AI model APIs
Vector databases
External tools and integrations

These operations take time. We cannot stop the entire JavaScript application while waiting for them. We need a mechanism that allows other work to continue while an operation is pending.

Promises represent these future results. async/await gives us a clean way to wait for those results within a particular function, handle success and failure, and continue the business workflow.

In simple words:

We use async/await to write asynchronous business logic in a readable, maintainable and structured way without blocking the entire JavaScript execution thread.

JavaScript Fetch API

1. Why Do We Need fetch()?

Let's take a real-world application. Imagine we are building an Employee List screen using Angular or React. We need to retrieve employee details from a backend API and display them in our frontend.

The Fetch API is a browser-provided API that allows JavaScript to communicate with servers using HTTP requests. 

fetch("https://api.example.com/employees");

This sends an HTTP request to the backend. By default, fetch() uses the GET method.

Important: fetch() does not immediately return employee data. It returns a Promise that will eventually provide a Response object.

4. Important: Does fetch() Reject for HTTP 404 or 500?

No, not automatically. This is one of the most important things to understand about the Fetch API.

Suppose the backend returns an HTTP 404 (Not Found) or 500 (Internal Server Error).

The server has still returned an HTTP response. Therefore, the fetch Promise normally fulfills with a Response object, even when the HTTP status indicates failure.

fetch(url)
|
+-- HTTP 200 → Promise fulfills
|
+-- HTTP 404 → Promise also fulfills
|
+-- HTTP 500 → Promise also fulfills

Check response.ok to identify HTTP success or failure.

To check whether the HTTP response was successful, use:

const response = await fetch(url);

if (!response.ok) {
    throw new Error(`HTTP Error: ${response.status}`);
}

Here:

  • response.ok is true for HTTP status codes from 200 to 299.
  • For other HTTP status codes, it is false.
  • throw new Error() makes the async function's Promise reject, allowing catch to handle the error.
What does fetch() reject automatically for? Examples include network failures, invalid request situations and aborted requests. Also, response.json() can reject if the response body cannot be parsed as valid JSON.

5. Complete Example — Fetch API with Error Handling

        const employees = await response.json();

        // Step 4: Use employee data
        console.log(employees);

    }

HTTP Error Handling in Fetch API

1. First, Understand the Real-World Scenario

Suppose our application requests a user from the backend API:

const response = await fetch("/api/users/999");

But the requested user does not exist in the backend. The server returns:

HTTP Status: 404 Not Found

The requested user could not be found.

Here comes an important concept about Fetch API.

2. fetch() Does NOT Automatically Reject for HTTP 404 or 500
async function getUser() {
    try {
        const response = await fetch("/api/users/999");

        console.log("Response received");

        const user = await response.json();

        console.log(user);

    } catch (error) {
        console.log("Caught:", error.message);
    }
}

getUser();

Even if the backend returns HTTP 404, the fetch Promise generally fulfills with a Response object.

Therefore, this statement executes:

console.log("Response received");

Why? Fetch considers whether it received an HTTP response. It does not automatically convert HTTP error status codes such as 404 or 500 into JavaScript exceptions.

Important distinction:

HTTP error response ≠ Network failure.

An HTTP 404 is still a valid HTTP response. A network failure means the request could not successfully obtain an HTTP response.

3. What Is response.ok?

response.ok is a Boolean property that tells us whether the HTTP status code indicates success.

HTTP Status Meaning response.ok
200 OK true
201 Created true
204 No Content true
400 Bad Request false
401 Unauthorized false
404 Not Found false
500 Internal Server Error false

When the HTTP status is between 200 and 299, response.ok is true. For other HTTP status codes, it is false.

How Do We Handle an Unsuccessful HTTP Response?
if (!response.ok) {
    throw new Error(`HTTP Error: ${response.status}`);
}
!response.ok
Checks whether the HTTP response indicates failure.
response.status
Provides the exact HTTP status code, such as 404 or 500.

throw new Error() creates a JavaScript error. This transfers execution to the matching catch block.

What does Bearer mean?

Bearer is an HTTP authentication scheme. It tells the server that the following value is a bearer access token.

User Login
↓

↓
Frontend sends Authorization Header
↓
Authorization: Bearer TOKEN
↓
Backend validates the token
↓
Access granted or rejected
Important: Sending a token does not guarantee access. The backend must verify whether the token is valid and whether the user is authorized to access the requested resource. Never put a real secret API key or sensitive credential directly into frontend source code.

AbortController – Cancel API Requests

Employee Search screen-ல் user வேகமாக type செய்கிறார் என்று வைத்துக்கொள்வோம்: R → Ra → Raj → Raja

ஒவ்வொரு input change-க்கும் API request அனுப்பப்படுகிறது. பழைய requests இன்னும் முடிவடையாமல் இருக்கலாம். அப்போது தேவையில்லாத requests-ஐ cancel செய்ய AbortController பயன்படுகிறது.

1. Create Controller

2. Pass Signal to Fetch 
signal: controller.signal
இந்த request-ஐ controller மூலம் cancel செய்யலாம்.
3. Cancel Request 
controller.abort();
Request-ஐ abort செய்கிறது.
Basic Example

    try {
        const response = await fetch("/api/employees", {
            signal: controller.signal
        });

        const employees = await response.json();
        console.log(employees);

    } catch (error) {
        if (error.name === "AbortError") {
            console.log("Request was cancelled");
        } else {
            console.log("API Error:", error);
        }
    }
}

Real-time Search – Cancel Previous Request

ஒவ்வொரு புதிய search-க்கும் பழைய request-ஐ cancel செய்து, புதிய AbortController உருவாக்க வேண்டும். 

let searchController;

async function searchEmployees(searchText) {

    // Cancel the previous request
    searchController?.abort();

    // Create a fresh controller for this request
    searchController = new AbortController();

    try {
        const response = await fetch(
            `/api/employees?search=${encodeURIComponent(searchText)}`,
            {
                signal: searchController.signal
            }
        );

        if (!response.ok) {
            throw new Error("Failed to fetch employees");
        }

        const employees = await response.json();
        console.log(employees);

    } catch (error) {
        if (error.name === "AbortError") {
            console.log("Previous search cancelled");
        } else {
            console.log(error);
        }
    }
}
How it works
  1. User types R → Request 1 starts.
  2. User types Ra → Request 1 cancelled; Request 2 starts.
  3. User types Raj → Request 2 cancelled; Request 3 starts.
  4. User types Raja → Request 3 cancelled; Request 4 starts.
Remember
  • One controller can cancel requests using its signal.
  • After aborting, that signal remains aborted. Create a new controller for the next request.
  • Cancellation usually causes Fetch to reject with an AbortError.
  • Client-side cancellation does not guarantee that the server has stopped processing the request.
Quick Revision: AbortController() → Creates controller; controller.signal → Connects it to Fetch; (Fetch request-க்கு cancellation signal கொடுக்கிறது) controller.abort() → Cancels the request. (அந்த signal-ஐ trigger செய்து request-ஐ abort செய்கிறது.) catch → Catches the AbortError.

const API_URL = "https://jsonplaceholder.typicode.com";

async function apiRequest(path, options = {}) {

    const response = await fetch(`${API_URL}${path}`, {
        ...options,
        headers: {
            Accept: "application/json",
            ...(options.body !== undefined
                ? { "Content-Type": "application/json" }
                : {}),
            ...options.headers

}

Sequential vs Parallel API Requests

Employee Dashboard-ல் இரண்டு API requests அனுப்ப வேண்டும் என்று வைத்துக்கொள்வோம்:

  1. Employee details பெற வேண்டும்.
  2. Department details பெற வேண்டும்.
1. Sequential API Requests

Sequential என்றால், முதல் request முடிந்த பிறகுதான் அடுத்த request ஆரம்பிக்கும். இங்கு இரண்டாவது API call, முதல் API call-ன் response கிடைத்த பிறகுதான் தொடங்குகிறது. 

async function loadDashboard() {

    const usersResponse = await fetch("/api/users");
    const users = await usersResponse.json();

    console.log("Users:", users);

    const departmentsResponse = await fetch("/api/departments");
    const departments = await departmentsResponse.json();

    console.log("Departments:", departments);
}

loadDashboard();
**Execution order:** Request 1 starts → Request 1 completes → Request 2 starts → Request 2 completes.
2. Parallel API Requests

இரண்டு requests-ம் ஒன்றையொன்று சார்ந்திருக்கவில்லை என்றால், இரண்டையும் ஒரே நேரத்தில் தொடங்கலாம். இதற்குப் Promise.all() பயன்படுத்தலாம். 

async function loadDashboard() {
    try {
        // Start both requests at the same time
        const [usersResponse, departmentsResponse] =
            await Promise.all([
                fetch("/api/users"),
                fetch("/api/departments")
            ]);

        if (!usersResponse.ok || !departmentsResponse.ok) {
            throw new Error("One or more API requests failed");
        }

        // Parse both responses concurrently
        const [users, departments] = await Promise.all([
            usersResponse.json(),
            departmentsResponse.json()
        ]);

        console.log("Users:", users);
        console.log("Departments:", departments);

    } catch (error) {
        console.log("Error:", error.message);
    }
}

loadDashboard();
**How Promise.all() works**
  • Accepts an array (or other iterable) of Promises.
  • Waits until all Promises fulfill.
  • Returns results in the same order as the input Promises.
  • If any Promise rejects, the returned Promise rejects immediately.
  • It does not automatically cancel the other pending requests.

When to Use Which?
Scenario Approach Reason
Get Employee ID, then fetch that employee's Orders Sequential Second request depends on the first response.
Get Users list and Products list independently Parallel Neither request depends on the other.
Get Department ID, then fetch Employees in that department Sequential Need the Department ID before making the second request.
**Quick Revision**
  • Sequential: One after another. Use when requests depend on previous results.
  • Parallel: Start independent requests together. Use Promise.all() to wait for all results.
