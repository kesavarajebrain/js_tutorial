Asynchronous JavaScript

Synchronous vs Asynchronous

Synchronous: Code executes one operation at a time, in order. The next operation waits for the current synchronous operation to finish.

தமிழில் - ஒத்திசைவு / ஒத்தியங்கு: ஒரு வேலையைச் செய்து முடித்த பிறகுதான் அடுத்த வேலையைச் செய்வது.

Asynchronous: Allows time-consuming operations, such as timers and API requests, to complete without blocking the rest of the JavaScript code while waiting.

தமிழில் - ஒத்திசையா / ஒத்தியங்கா: ஒரு வேலையின் முடிவுக்காகக் காத்திருக்கும்போது, மற்ற code தொடர்ந்து இயங்க அனுமதிக்கும் முறை.

1. Synchronous Code
console.log("A");
console.log("B");
console.log("C");
Output 
A
B
C

Each statement finishes before the next statement executes.

2. Asynchronous Code
console.log("A");

setTimeout(() => {
    console.log("B");
}, 1000);

console.log("C");
Output 
A
C
B

setTimeout() schedules the callback to run after approximately 1 second. Meanwhile, JavaScript continues to the next statement.

3. Understand the Execution Order
console.log("A") → Prints A
setTimeout(...) → Schedules the callback
console.log("C") → Prints C
Timer finishes → Callback becomes eligible to run
Event loop → Callback runs when JavaScript can execute it
console.log("B") → Prints B
Important: The 1000 milliseconds is a minimum delay before the callback becomes eligible to execute, not a guarantee that it runs at exactly 1 second.
4. Does Asynchronous Mean JavaScript Runs Two Pieces of Code Simultaneously?

No, not automatically. JavaScript normally executes one piece of JavaScript code at a time on its main thread. The runtime, queues and event loop coordinate asynchronous callbacks so that JavaScript can continue working instead of waiting synchronously for every operation.

Quick Revision

Synchronous → Execute in order; the next operation waits for the current one to finish.

Asynchronous → Schedule or handle work that can complete later, allowing the remaining code to continue while waiting.

Single-threaded

Example: One cashier

One cashier serves customers one at a time. The next customer waits until the current service is finished.
One cashier
Customer 1 → Customer 2 → Customer 3

ஒரு நேரத்தில் ஒரு வேலையை மட்டும் execute செய்யும் ஒரு execution path.

Multithreading

Example: Multiple cashiers

Multiple cashiers serve different customers at the same time.
Cashier 1 → Customer 1
Cashier 2 → Customer 2
Cashier 3 → Customer 3

பல execution paths இருப்பதால், பல threads தனித்தனியாக வேலை செய்யலாம்.

Remember:
Single-threaded = One execution path at a time.
Multithreading = Multiple execution paths that can make progress independently and, on multiple CPU cores, may run simultaneously.

"நான் முடிஞ்சதும் மட்டும் அடுத்தது தொடங்கும்."

ஒவ்வொரு synchronous operation-உம் முடிந்த பிறகுதான் அடுத்த statement execute ஆகும். நீண்ட நேரம் எடுக்கும் operation, அதே thread-ல் அடுத்த code இயங்குவதைத் தடுக்கலாம் (block செய்யலாம்).

2. Asynchronous

"நான் முடியும் வரை காத்திருக்காதே; அடுத்த வேலையைத் தொடங்கு."

Line 1 → Start operation
↓
Line 2 → Line 3
↓
Result arrives later

ஒரு asynchronous operation-ஐத் தொடங்கிவிட்டு, அதன் முடிவுக்காக JavaScript thread-ஐ நிறுத்தாமல் அடுத்த code-ஐ execute செய்யலாம்.

3. Key Point: Async Does NOT Mean "Runs on Another Thread"

Asynchronous ≠ Multithreaded

Async என்பது வேறொரு JavaScript thread-ல் code இயங்குகிறது என்று அர்த்தமல்ல. ஒரு single JavaScript thread-லேயே asynchronous programming செய்யலாம்.

Browser அல்லது Node.js runtime, timer மற்றும் network போன்ற asynchronous operations-ஐ manage செய்யும். Operation முடிந்ததும், callback அல்லது continuation execute ஆவதற்குத் தயாராகும். Event loop, JavaScript எப்போது அந்த callback-ஐ இயக்க முடியும் என்பதை coordinate செய்கிறது.

JavaScript Thread
Start async operation
↓
Continue executing other JS code
↓
Runtime handles waiting / I/O
↓
Result or callback becomes ready
↓
JS thread executes the callback

Example:

console.log("A");

setTimeout(() => {
    console.log("B");
}, 1000);

console.log("C");

Output: A → C → B

setTimeout() timer-ஐ schedule செய்கிறது. JavaScript அதற்காக ஒரு second முழுவதும் காத்திருக்காமல் "C"-ஐ print செய்கிறது. Timer முடிந்ததும் callback பின்னர் execute ஆகும்.

Note: Browser மற்றும் Node.js runtime-கள் தங்களுக்குள் threads அல்லது பிற system resources-ஐப் பயன்படுத்தலாம். ஆனால் சாதாரண main-thread JavaScript callbacks ஒவ்வொன்றாகத்தான் execute ஆகும். Web Workers போன்ற வசதிகள் மூலம் JavaScript-ல் கூடுதல் threads-ஐயும் பயன்படுத்தலாம்.

Web APIs — How Does JavaScript Handle Asynchronous Operations?

JavaScript single-threaded என்றால், setTimeout() போன்ற asynchronous operations-ஐ யார் handle செய்கிறார்கள்?

Answer: The JavaScript runtime environment provides additional capabilities through APIs. In a browser, these include timer, network and DOM APIs. These capabilities are separate from the core JavaScript language.

1. What If We Have Only JavaScript?

JavaScript language provides variables, functions, loops, objects and built-in features. When JavaScript runs in a browser, it can also use the additional capabilities provided by the browser. 

console.log("Start");

setTimeout(() => {
    console.log("Timer finished");
}, 2000);

console.log("End");

Output:

Start
End
Timer finished

Here, setTimeout() is not core JavaScript syntax. It is a timer API provided by the runtime environment. The browser manages the timer while JavaScript continues executing the next statement.

2. What Are Web APIs?

Web APIs are capabilities exposed by the browser that JavaScript code can use. They let web applications interact with timers, web pages, network requests, user events and other browser features.

Timer API
setTimeout(), setInterval()

Schedule a callback to run after a delay or repeatedly at intervals.

Network API
fetch()

Make HTTP requests and handle responses from servers.

DOM APIs
document, event listeners

Access and update web page elements and respond to user interactions.

Other Browser APIs
Examples include storage, notifications and geolocation APIs.

Provide access to additional browser capabilities, subject to permissions where required.

Important: Not every Web API is asynchronous. For example, many DOM property accesses are synchronous. Web APIs include both synchronous and asynchronous functionality.

3. How Does the Browser Expose These APIs to JavaScript?

When a browser runs JavaScript in a web page, it provides a global environment with access to browser APIs. That's why you can call setTimeout() without importing it.

For example, in a browser:

console.log(typeof setTimeout);        // "function"
console.log(typeof window.setTimeout); // "function"

window.setTimeout(() => {
    console.log("Hello");
}, 1000);

You don't need a separate JavaScript import for these built-in browser APIs. The browser exposes them through the environment in which your code runs.

↓
JavaScript calls the API
↓
Browser manages the timer
↓
Callback becomes eligible to run
↓
Event loop coordinates when the callback executes

JavaScript doesn't run only in browsers. Node.js can also execute JavaScript, but it provides a different runtime environment.

setTimeout() works in Node.js too. That doesn't mean Node.js is running a browser. Node.js provides its own timer APIs and other capabilities, such as filesystem access.

Callback Task Queue or Macrotask queue — Where Does a Callback Wait?

நாம் ஏற்கெனவே புரிந்துகொண்டது:

  • Browser timer-ஐ schedule செய்கிறது.
  • Timer முடிந்ததும், callback execute செய்யத் தயாராகிறது.
  • JavaScript main thread ஏற்கெனவே synchronous code-ஐ execute செய்துகொண்டிருந்தால், callback அதை இடைமறித்து run ஆக முடியாது.

Question: Execute செய்யத் தயாராக இருக்கும் callback எங்கே காத்திருக்கும்?

Answer: Callback Task Queue-ல் காத்திருக்கலாம்.

Callback தனது turn-க்காகக் காத்திருக்கிறது
↓ Callback execute ஆகிறது

Remember:

Callback Queue என்பது தனியாக ஒரு thread அல்ல; அது waiting callbacks-க்கான queue.

Microtask Queue vs Callback Task Queue

Macro - BIG, Micro - small

நாம் ஏற்கெனவே கற்றுக்கொண்டது: Timer முடிந்த பிறகு அதன் callback execute ஆகத் தயாராகி Task Queue-ல் காத்திருக்கும். ஆனால் எல்லா asynchronous callbacks-உம் ஒரே queue-ல் காத்திருப்பதில்லை.

JavaScript runtime-ல் இரண்டு முக்கியமான scheduling mechanisms உள்ளன:

1. Callback Task Queue

Ordinary Tasks

  • setTimeout()
  • setInterval()
  • Many DOM event callbacks
  • Other browser tasks

Task execute செய்யத் தயாரான பிறகு தனது turn-க்காகக் காத்திருக்கும்.

2. Microtask Queue

Microtasks

  • Promise.then()
  • Promise.catch()
  • Promise.finally()
  • queueMicrotask()

Microtask checkpoint-இல் execute செய்யப்படுவதற்காகக் காத்திருக்கும்.

Important: Microtask Queue என்பது Task Queue-ஐ விட முன்னுரிமையாக process செய்யப்படும் தனி queue. இது ஒரே queue-ல் priority கொடுப்பது போன்றது அல்ல; இரண்டும் தனித்தனியான scheduling mechanisms.

1. How Does the Browser Process These Queues?

Current JavaScript task முடிந்ததும், browser microtask checkpoint-ஐச் செய்கிறது. அதாவது, Microtask Queue-ல் இருக்கும் microtasks அனைத்தும் empty ஆகும் வரை ஒவ்வொன்றாக execute செய்யப்படும். அதன் பிறகு browser அடுத்த task-ஐ process செய்யலாம்; rendering-க்கும் வாய்ப்பு கிடைக்கலாம்.

Current JavaScript Task finishes
↓
Microtask Queue
↓
Process microtasks until EMPTY
↓
Rendering opportunity (when applicable)
↓
Next Task from a Task Queue
↓
Next Microtask Checkpoint
Remember: Microtasks are processed before the event loop moves on to another task. If a microtask adds another microtask, that new microtask is also processed in the same checkpoint.

2. First Example — Promise vs setTimeout vs queueMicrotask

console.log("Start");

setTimeout(() => {
    console.log("Timer callback");
}, 0);

Promise.resolve().then(() => {
    console.log("Promise microtask");
});

queueMicrotask(() => {
    console.log("Direct microtask");
});

console.log("End");
Final Output
Start
End
Promise microtask
Direct microtask
Timer callback
Why This Output?

Let's follow the execution order:

Step Operation Where It Goes
1 console.log("Start") Executes immediately
2 setTimeout() Schedules a Timer Task
3 Promise.then() Microtask Queue
4 queueMicrotask() Microtask Queue
5 console.log("End") Executes immediately
6 Microtask checkpoint Promise callback, then Direct microtask
7 Timer Task Timer callback executes later

Why does Promise execute before setTimeout? Because Promise callbacks are microtasks, and microtasks are drained before the next ordinary task is processed.

Why does Promise microtask execute before Direct microtask? Both are added to the Microtask Queue in that order. The queue follows FIFO (First In, First Out) ordering.

Note: setTimeout(..., 0) does not mean the callback runs immediately. It becomes eligible after the timer delay and runs when the event loop gets to its task. Here, the microtasks run first.

3. FIFO — What Happens When One Microtask Adds Another?

Let's understand an interesting case: a microtask can schedule another microtask while the queue is already being processed. 

console.log("Start");

queueMicrotask(() => {
    console.log("M1 - A");

    queueMicrotask(() => {
        console.log("M2");
    });

    console.log("M1 - B");
});

queueMicrotask(() => {
    console.log("M3");
});

console.log("End");
Final Output
Start
End
M1 - A
M1 - B
M3
M2
Understand the Queue Step by Step

Before microtask processing begins, the first two microtasks are already queued.

Initial Microtask Queue
┌──────────┐
│ M1 │
│ M3 │
└──────────┘
Step What Happens Remaining Queue
1 M1 starts and prints M1 - A. M3
2 M1 schedules M2 at the end of the queue. M3 → M2
3 M1 prints M1 - B and finishes. M3 → M2
4 M3 executes. M2
5 M2 executes. Empty
Important: M2 does not jump ahead of M3. It is added to the end of the Microtask Queue, so M3 executes first.

5. Microtask Starvation

We know that the browser processes microtasks until the Microtask Queue becomes empty.

But what happens when microtasks continuously add more microtasks?

This can cause a problem called Microtask Starvation.

Example: Scheduling Microtasks Repeatedly

let count = 1;

    console.log("Microtask", count);

    if (count < 3) {
        count++;
        queueMicrotask(repeatMicrotask);
    }
}

setTimeout(() => {
    console.log("Timer");
}, 0);

queueMicrotask(repeatMicrotask);

console.log("End");

Microtask 3

Why does the Timer execute last?

  1. The timer callback is scheduled as a task.
  2. repeatMicrotask is added to the Microtask Queue.
  3. The current JavaScript task finishes, and the microtask checkpoint begins.
  4. Microtask 1 schedules Microtask 2.
  5. Microtask 2 schedules Microtask 3.
  6. The queue becomes empty only after Microtask 3 finishes.
  7. Now the event loop can move on to the Timer task.

6. What If We Remove the Condition?

Imagine removing this condition:

if (count < 3) {
    count++;
    queueMicrotask(repeatMicrotask);
}

And always scheduling another microtask:

function repeatMicrotask() {
    console.log("Microtask", count++);
    queueMicrotask(repeatMicrotask);
}

Now each microtask schedules another microtask forever. The Microtask Queue never becomes empty.

Microtask Starvation

When microtasks continuously schedule more microtasks, the browser may never get an opportunity to process the next task or update the page.

This can:

  • Delay timer callbacks.
  • Delay browser rendering and UI updates.
  • Make a webpage appear frozen or unresponsive.

Why is this dangerous? The browser drains microtasks before moving on to another task. If that drain never finishes, other work cannot get its normal turn.

1. First, Why Were Callbacks Introduced?

Callbacks allow us to execute a function after an asynchronous operation finishes and provide its result to another function.

3. What Exactly Is Callback Hell?

When multiple asynchronous operations depend on each other, we may end up placing callbacks inside other callbacks, creating deeply nested code.

Let's look at the same e-commerce workflow using nested callbacks.

getUser(101, function(user) {

    getOrders(user.id, function(orders) {

        getOrderDetails(orders[0].id, function(orderDetails) {

            getShippingDetails(orderDetails.addressId, function(shipping) {

                console.log(user);
                console.log(orders);
                console.log(orderDetails);
                console.log(shipping);

            });

        });

    });

});

Here, assume each function performs an asynchronous operation and invokes its callback when the result is ready.

Look at the Structure
getUser()
└── getOrders()
    └── getOrderDetails()
        └── getShippingDetails()
            └── Display Result

Every callback is nested inside the previous callback. As more dependent operations are added, the code moves further and further to the right.

This structure is commonly called:
  • Callback Hell
  • Pyramid of Doom

4. Why Is Callback Hell a Problem?

Deep Nesting

Too many nested callbacks make the code difficult to follow.

Readability

Understanding the execution flow becomes harder.

Error Handling

Each asynchronous operation may need separate error handling.

Maintenance

Changing or debugging deeply nested code becomes more difficult.

5. Important: Callbacks Are Not Bad

Callbacks are still useful and widely used in JavaScript. The problem is not callbacks themselves; it is excessive nesting of dependent asynchronous callbacks.

Final Takeaway

Callback = A function passed to another function to be executed later or at a particular point.

Callback Hell = Deeply nested callbacks that make asynchronous code difficult to read, maintain and handle errors in.

Think of these as the evolution of writing and managing asynchronous JavaScript code. The goal was to make asynchronous operations easier to organize, read, maintain and handle errors.

Important Things to Understand

1. Callbacks are not always asynchronous.

A callback is simply a function passed to another function. It can execute immediately or later, depending on how the receiving function uses it.

2. Promises have three states.

3. async functions always return a Promise.

Even when you return a normal value from an async function, JavaScript wraps the result in a fulfilled Promise.

JavaScript Promises

1. What Exactly Is a Promise?

A Promise is a JavaScript object that represents the eventual result of an operation. That result may be a success or a failure.

Imagine ordering food online:

1. Order
You place an order.
2. Pending (there is no explicit method)
Restaurant prepares the food.
3. Success (Fulfilled / method - resolve)
Food is delivered.
OR Failure (Rejected / method - reject)

Order is cancelled.

You don't have the final result immediately. The Promise represents the operation's eventual outcome.

The function passed inside new Promise() is called the executor function.

Important: The executor function runs immediately and synchronously when the Promise is created. The Promise constructor itself does not automatically make the executor asynchronous.

    console.log("Executor started");

    const paymentSuccessful = true;

    if (paymentSuccessful) {
        resolve("Payment successful");
    } else {
        reject("Payment failed");

});

What's Happening?
  1. new Promise() creates a Promise object.
  2. The executor function runs immediately.
  3. We check whether the payment was successful.
  4. resolve() or reject() settles the Promise.
  5. The remaining synchronous code continues.
Remember: Promise executor = Synchronous execution. The operation inside it can be asynchronous when we use APIs such as setTimeout() or fetch().

4. What Are the Three States of a Promise?

A Promise has exactly three states:

1. Pending
Waiting

The operation has not yet settled. Its outcome is not known.

2. Fulfilled
Success

resolve(value) successfully fulfills the Promise.

3. Rejected

Failure

reject(reason) rejects the Promise.
Pending
├── resolve(value) → Fulfilled
└── reject(reason) → Rejected

Fulfilled / Rejected = Settled

Important: Once a Promise is fulfilled or rejected, its state cannot change again. This is called a settled Promise.

5. What Happens If resolve() and reject() Are Both Called?

const promise = new Promise((resolve, reject) => {

    resolve("Success");
    reject("Failure");

});

Here, the Promise becomes fulfilled with "Success". The subsequent reject() cannot change its state.

Remember: First settlement wins.

Once the Promise has been fulfilled or rejected, subsequent attempts to settle it have no effect.

Every .then() returns a new Promise.

3. What Exactly Does Each .then() Return?

This is important to understand deeply:

Return a Normal Value
.then(() => {
    return 100;
})

The new Promise fulfills with 100.

Return Another Promise
.then(() => {
    return getUser();
})

The next .then() waits for that Promise to settle and receives its fulfillment value.

No return statement 
.then(() => {
    console.log("Hello");
})

The new Promise fulfills with undefined.

Throw an Error 
.then(() => {
    throw new Error("Failed");
})

The new Promise becomes rejected, and the rejection can be handled by a following .catch().

Golden Rule: Return a value to pass it to the next .then(). Return a Promise to make the chain wait for that asynchronous operation. Use throw to pass an error into the rejection path.

Promise Error Handling — .catch() and .finally()

1. What Happens When a .then() Throws an Error?

When an error is thrown inside a .then() callback, the Promise returned by that .then() becomes rejected. The remaining success handlers are skipped until a rejection handler handles the error.

Promise.resolve(10)
    .then((value) => {
        console.log("First:", value);
        throw new Error("Something went wrong");
    })
    .then((value) => {
        console.log("Second:", value);
    })
    .catch((error) => {
        console.log("Error:", error.message);
    });
Output
First: 10
Error: Something went wrong

Why didn't the Second .then() execute?

Promise.resolve(10)
↓
First .then() → Prints 10
↓
throw new Error()
↓
Returned Promise becomes REJECTED
↓
Second .then() → Skipped
↓
.catch() → Handles the error
Remember: A thrown error inside a Promise callback turns the returned Promise into a rejected Promise. The next success handler is skipped, and the error travels down the chain until a rejection handler handles it.

2. One .catch() Can Handle Errors from Multiple Operations

One of the major advantages of Promise chaining is that we can handle errors from multiple preceding asynchronous operations using a single .catch().

getUser()
↓
getOrders(user.id)
↓
getOrderDetails(orders[0].id)
↓
Display Details

Any rejection / thrown error
↓
.catch() 
getUser()
    .then(user => getOrders(user.id))
    .then(orders => getOrderDetails(orders[0].id))
    .then(details => console.log(details))
    .catch(error => {
        console.log("Error:", error);
    });

The final .catch() can handle a rejection or an error thrown anywhere in the preceding Promise chain, provided the error is represented as a rejection in that chain.

Important: A synchronous error thrown while initially calling getUser() before it returns a Promise is not automatically caught by the attached .catch(). The chain must first be established as a Promise chain.

3. What Is .finally()?

.finally() executes whether the Promise is fulfilled or rejected. It is useful for cleanup operations, such as hiding a loading indicator or releasing resources.

Promise.resolve("Success")
    .then(value => {
        console.log(value);
    })
    .finally(() => {
        console.log("Operation completed");
    });

Output:

Success
Operation completed

It also executes when the Promise is rejected:

Promise.reject("Failed")
    .catch(error => {
        console.log(error);
    })
    .finally(() => {
        console.log("Operation completed");
    });

Output:

Failed
Operation completed
How Is .finally() Different from .then() and .catch()?
Method When It Executes Purpose
.then() When fulfilled (success handler). Process the successful result.
.catch() When rejected (rejection handler). Handle errors.
.finally() When fulfilled or rejected. Perform cleanup or final actions.
Important: .finally() normally preserves the original Promise outcome. It doesn't receive the fulfillment value or rejection reason as an argument.

5. Important Detail — Does .finally() Always Preserve the Result?

Normally, yes. But there is one important exception: if the .finally() callback throws an error or returns a rejected Promise, the resulting Promise becomes rejected.

Promise.resolve(100)
    .finally(() => {
        throw new Error("Finally failed");
    })
    .then(value => {
        console.log(value);
    })
    .catch(error => {
        console.log(error.message);
    });

Output:

Finally failed

Here, the original value 100 is not passed to the success handler because the error thrown inside .finally() changes the resulting Promise into a rejected state.

JavaScript Promise Combinators

Promise Combinators are built-in static methods that help us work with multiple Promises together. Depending on the requirement, we can wait for all Promises, wait for the first result, or collect every outcome.

1. Four Important Promise Combinators
Method Main Purpose Outcome
Promise.all() Waits for all Promises to fulfill. Rejects if any one Promise rejects.
Promise.allSettled() Waits for all Promises to settle. Returns every fulfilled or rejected outcome.
Promise.race() Waits for the first Promise to settle. Returns the first fulfillment or rejection.
Promise.any() Waits for the first Promise to fulfill. Rejects with AggregateError if all reject.

Remember: settle means either fulfilled or rejected.

2. Promise.all() — All Must Fulfill

Imagine an employee dashboard that needs three independent API responses:

Employee API
Employee details
Department API
Department details
Projects API
Project details

These requests are independent. We can start all three without waiting for one to finish before starting the next.

const employeePromise =
    Promise.resolve("Employee details");

const departmentPromise =
    Promise.resolve("Department details");

const projectPromise =
    Promise.resolve("Project details");

Promise.all([
    employeePromise,
    departmentPromise,
    projectPromise
])
.then((results) => {
    console.log(results);
})
.catch((error) => {
    console.log(error);
});
Output
[
    "Employee details",
    "Department details",
    "Project details"
]

How does it work?

  • Promise.all() receives multiple Promises.
  • It waits until all of them fulfill.
  • It returns an array containing all fulfillment values.
  • The result order matches the input order, not the order in which the requests finish.
Remember: Promise.all() = All must fulfill. Even if one Promise rejects, the returned Promise rejects without waiting for the remaining Promises to fulfill.
Important: Promise.all() does not automatically cancel the other operations when one rejects. Those operations may continue running.

3. Real-World Example — Multiple API Calls

In a real application, fetch() already returns a Promise. We don't need to create a new Promise manually just to make an API request.

const employeePromise =
    fetch("/api/employee")
        .then(res => {
            if (!res.ok) throw new Error("Employee API failed");
            return res.json();
        });

const departmentPromise =
    fetch("/api/department")
        .then(res => {
            if (!res.ok) throw new Error("Department API failed");
            return res.json();
        });

const projectPromise =
    fetch("/api/projects")
        .then(res => {
            if (!res.ok) throw new Error("Projects API failed");
            return res.json();
        });

Promise.all([
    employeePromise,
    departmentPromise,
    projectPromise
])
.then(([employee, department, projects]) => {
    console.log(employee);
    console.log(department);
    console.log(projects);
})
.catch(error => {
    console.log("Dashboard loading failed:", error.message);
});

Notice this syntax:

.then(([employee, department, projects]) => {
    // Use each API response
});

This is array destructuring. Promise.all() returns an array, and we extract its values into separate variables.

Fetch important detail: A server response such as HTTP 404 or 500 does not automatically reject a fetch Promise. Checking response.ok and throwing an error ensures those HTTP failures enter the .catch() path. Network errors and JSON parsing errors can also reject the chain.

4. Promise.allSettled() — Wait for Every Outcome

Wait for all Promises to finish, regardless of whether they succeed or fail

const p1 = Promise.resolve("Employee details");
const p2 = Promise.reject("Department API failed");
const p3 = Promise.resolve("Project details");

Promise.allSettled([p1, p2, p3])
    .then(results => {
        console.log(results);
    });
Output
[
    { status: "fulfilled", value: "Employee details" },
    { status: "rejected", reason: "Department API failed" },
    { status: "fulfilled", value: "Project details" }
]

Unlike Promise.all(), one rejected Promise does not cause the combined Promise to reject. It waits for every input Promise to settle and reports each outcome.

Use case: A dashboard where you want to display whichever sections loaded successfully, while separately showing errors for failed sections.

5. Promise.race() — First Promise to Settle Wins

Promise.race() returns the outcome of whichever Promise settles first. That could be a success or a failure.

const p1 = new Promise(resolve => {
    setTimeout(() => resolve("First API"), 1000);
});

const p2 = new Promise(resolve => {
    setTimeout(() => resolve("Second API"), 2000);
});

Promise.race([p1, p2])
    .then(result => {
        console.log(result);
    })
    .catch(error => {
        console.log(error);
    });
Output
First API

p1 fulfills after approximately 1 second, while p2 fulfills after approximately 2 seconds. Therefore, p1 wins the race.

Important: Promise.race() doesn't cancel the losing Promises. They continue running unless you explicitly cancel the underlying operation where supported.
Use case: Implementing a timeout or selecting whichever of multiple requests responds first.

6. Promise.any() — First Successful Promise Wins

What if the first Promise fails, but another Promise succeeds? With Promise.any(), we don't care about the first rejection. We want the first successful result.

const p1 = Promise.reject("Server 1 failed");

const p2 = new Promise(resolve => {
    setTimeout(() => resolve("Server 2 success"), 1000);
});

const p3 = new Promise(resolve => {
    setTimeout(() => resolve("Server 3 success"), 2000);
});

Promise.any([p1, p2, p3])
    .then(result => {
        console.log(result);
    })
    .catch(error => {
        console.log(error);
    });
Output
Server 2 success

Although the first Promise rejects immediately, Promise.any() continues waiting for a successful result. Server 2 fulfills first, so its result is returned.

What if all Promises reject? Promise.any() rejects with an AggregateError, which contains the rejection reasons in its errors property. 
Promise.any([
    Promise.reject("Server 1 failed"),
    Promise.reject("Server 2 failed")
])
.catch(error => {
    console.log(error instanceof AggregateError); // true
    console.log(error.errors);
    // ["Server 1 failed", "Server 2 failed"]
});
Use case: Trying multiple servers or service providers and accepting whichever one succeeds first.

7. All Four Methods — Side-by-Side Comparison

Method Waits For What Determines the Result?
all() All Promises to fulfill All must succeed; one rejection rejects the combined Promise.
allSettled() All Promises to settle Collects every success and failure.
race() First Promise to settle First success OR failure wins.
any() First Promise to fulfill First success wins; all failures produce AggregateError.
One additional point: Array map() itself is synchronous, but you can use an asynchronous callback with it. In that case, it returns an array of Promises, and Promise.all() is commonly used to collect their results. 
const ids = [101, 102, 103];

const promises = ids.map(id => fetch(`/api/users/${id}`));

Promise.all(promises).then(responses => {
    console.log(responses);
});

JavaScript async / await

async/await is modern JavaScript syntax for working with Promises. It makes asynchronous code easier to read and write because it looks similar to normal sequential JavaScript.

1. Why Do We Need async/await?

Remember our Promise chaining example with multiple dependent API calls:

getUser(101)
    .then(user => {
        return getOrders(user.id);
    })
    .then(orders => {
        return getOrderDetails(orders[0].id);
    })
    .then(details => {
        console.log(details);
    })
    .catch(error => {
        console.log(error);
    });

Now look at the same workflow using async/await:

async function loadOrder() {
    try {
        const user = await getUser(101);

        const orders = await getOrders(user.id);

        const details = await getOrderDetails(orders[0].id);

        console.log(details);

    } catch (error) {
        console.log(error);
    }
}

loadOrder();

See the difference? The code looks sequential and is easier to read. Each await waits for the previous operation's result before continuing the function.

Remember: async/await does not replace Promises. It is a cleaner way to work with Promise-based operations.

2. What Does async Do?

When we add async before a function, that function always returns a Promise, even when we return a normal value.

async function greet() {
    return "Hello";
}

const result = greet();

console.log(result);

The result is a Promise fulfilled with "Hello".

Conceptually, returning a normal value from an async function is similar to:

function greet() {
    return Promise.resolve("Hello");
}

We can consume the result using .then():

greet().then(result => {
    console.log(result); // Hello
});
Important: An async function can have zero or more await expressions. Even without await, it still returns a Promise.

3. What Does await Do?

await performs two important jobs:

1. Gets the Fulfilled Value

It gives us the actual fulfillment value instead of making us work directly with the Promise object.

const name = await getName();

// name = "John"
2. Suspends the Async Function

It pauses the remaining execution of the current async function until the awaited operation settles.

const name = await getName();

// Remaining code
// resumes later

Important: await does not block the entire JavaScript thread. Other JavaScript work can continue while the async function is suspended.

Example: await with an Asynchronous Operation
function getEmployee() {
    return new Promise(resolve => {
        setTimeout(() => {
            resolve("Employee details");
        }, 2000);
    });
}

async function loadEmployee() {
    console.log("Start");

    const result = await getEmployee();

    console.log(result);
    console.log("End");
}

loadEmployee();

console.log("Outside");

Start
Outside

// After approximately 2 seconds:
Employee details
End

6. Position of await Matters

The position where we write await determines which statements execute immediately and which statements resume later.

Example A — await After Start
function getName() {
    return Promise.resolve("John");
}

async function test() {
    console.log("Start");

    const name = await getName();

    console.log("Name:", name);
    console.log("End");
}

console.log("A");
test();
console.log("B");
Output 
A
Start
B
Name: John
End

Start executes before await. The function suspends at await, allowing B to execute first.

Example B — await Before Start
function getName() {
    return Promise.resolve("John");
}

async function test() {
    const name = await getName();

    console.log("Start");
    console.log("Name:", name);
    console.log("End");

A
B
Start

End

Here, the function reaches await immediately and suspends. Therefore, B executes before all the remaining statements.

Golden Rule: Code before the first await executes immediately. Code after an await resumes later, even if the awaited Promise is already fulfilled.

8. How Does await Handle a Rejected Promise?

When an awaited Promise is rejected, await throws the rejection reason inside the async function. We can handle it with normal try/catch.

async function loadEmployee() {
    try {
        const employee = await Promise.reject(
            new Error("Employee not found")
        );

        console.log(employee);

    } catch (error) {
        console.log("Error:", error.message);
    }
}

loadEmployee();

Output:

Error: Employee not found

This is one reason async/await is convenient: Promise rejections can be handled using familiar synchronous-looking try/catch syntax.
