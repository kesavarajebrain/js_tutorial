Asynchronous JavaScript

Synchronous vs Asynchronous

Synchronous: Code executes one operation at a time, in order. The next operation waits for the current synchronous operation to finish.

தமிழில் - ஒத்திசைவு / ஒத்தியங்கு: ஒரு வேலையைச் செய்து முடித்த பிறகுதான் அடுத்த வேலையைச் செய்வது.

Asynchronous: Allows time-consuming operations, such as timers and API requests, to complete without blocking the rest of the JavaScript code while waiting.

தமிழில் - ஒத்திசையா / ஒத்தியங்கா: ஒரு வேலையின் முடிவுக்காகக் காத்திருக்கும்போது, மற்ற code தொடர்ந்து இயங்க அனுமதிக்கும் முறை.

1. Synchronous Code
console.log("A");
console.log("B");
console.log("C");
Output 
A
B
C

Each statement finishes before the next statement executes.

2. Asynchronous Code
console.log("A");

setTimeout(() => {
    console.log("B");
}, 1000);

console.log("C");
Output 
A
C
B

setTimeout() schedules the callback to run after approximately 1 second. Meanwhile, JavaScript continues to the next statement.

3. Understand the Execution Order
console.log("A") → Prints A
setTimeout(...) → Schedules the callback
console.log("C") → Prints C
Timer finishes → Callback becomes eligible to run
Event loop → Callback runs when JavaScript can execute it
console.log("B") → Prints B
Important: The 1000 milliseconds is a minimum delay before the callback becomes eligible to execute, not a guarantee that it runs at exactly 1 second.
4. Does Asynchronous Mean JavaScript Runs Two Pieces of Code Simultaneously?

No, not automatically. JavaScript normally executes one piece of JavaScript code at a time on its main thread. The runtime, queues and event loop coordinate asynchronous callbacks so that JavaScript can continue working instead of waiting synchronously for every operation.

Quick Revision

Synchronous → Execute in order; the next operation waits for the current one to finish.

Asynchronous → Schedule or handle work that can complete later, allowing the remaining code to continue while waiting.

Single-threaded

Example: One cashier

One cashier serves customers one at a time. The next customer waits until the current service is finished.
One cashier
Customer 1 → Customer 2 → Customer 3

ஒரு நேரத்தில் ஒரு வேலையை மட்டும் execute செய்யும் ஒரு execution path.

Multithreading

Example: Multiple cashiers

Multiple cashiers serve different customers at the same time.
Cashier 1 → Customer 1
Cashier 2 → Customer 2
Cashier 3 → Customer 3

பல execution paths இருப்பதால், பல threads தனித்தனியாக வேலை செய்யலாம்.

Remember:
Single-threaded = One execution path at a time.
Multithreading = Multiple execution paths that can make progress independently and, on multiple CPU cores, may run simultaneously.

ஒவ்வொரு synchronous operation-உம் முடிந்த பிறகுதான் அடுத்த statement execute ஆகும். நீண்ட நேரம் எடுக்கும் operation, அதே thread-ல் அடுத்த code இயங்குவதைத் தடுக்கலாம் (block செய்யலாம்).

2. Asynchronous

"நான் முடியும் வரை காத்திருக்காதே; அடுத்த வேலையைத் தொடங்கு."

Line 1 → Start operation
↓
Line 2 → Line 3
↓
Result arrives later

ஒரு asynchronous operation-ஐத் தொடங்கிவிட்டு, அதன் முடிவுக்காக JavaScript thread-ஐ நிறுத்தாமல் அடுத்த code-ஐ execute செய்யலாம்.

3. Key Point: Async Does NOT Mean "Runs on Another Thread"

Asynchronous ≠ Multithreaded

Async என்பது வேறொரு JavaScript thread-ல் code இயங்குகிறது என்று அர்த்தமல்ல. ஒரு single JavaScript thread-லேயே asynchronous programming செய்யலாம்.

Browser அல்லது Node.js runtime, timer மற்றும் network போன்ற asynchronous operations-ஐ manage செய்யும். Operation முடிந்ததும், callback அல்லது continuation execute ஆவதற்குத் தயாராகும். Event loop, JavaScript எப்போது அந்த callback-ஐ இயக்க முடியும் என்பதை coordinate செய்கிறது.

JavaScript Thread
Start async operation
↓
Continue executing other JS code
↓
Runtime handles waiting / I/O
↓
Result or callback becomes ready
↓
JS thread executes the callback

Example:

console.log("A");

setTimeout(() => {
    console.log("B");
}, 1000);

console.log("C");

Output: A → C → B

setTimeout() timer-ஐ schedule செய்கிறது. JavaScript அதற்காக ஒரு second முழுவதும் காத்திருக்காமல் "C"-ஐ print செய்கிறது. Timer முடிந்ததும் callback பின்னர் execute ஆகும்.

Note: Browser மற்றும் Node.js runtime-கள் தங்களுக்குள் threads அல்லது பிற system resources-ஐப் பயன்படுத்தலாம். ஆனால் சாதாரண main-thread JavaScript callbacks ஒவ்வொன்றாகத்தான் execute ஆகும். Web Workers போன்ற வசதிகள் மூலம் JavaScript-ல் கூடுதல் threads-ஐயும் பயன்படுத்தலாம்.

Web APIs — How Does JavaScript Handle Asynchronous Operations?

JavaScript single-threaded என்றால், setTimeout() போன்ற asynchronous operations-ஐ யார் handle செய்கிறார்கள்?

Answer: The JavaScript runtime environment provides additional capabilities through APIs. In a browser, these include timer, network and DOM APIs. These capabilities are separate from the core JavaScript language.

1. What If We Have Only JavaScript?

JavaScript language provides variables, functions, loops, objects and built-in features. When JavaScript runs in a browser, it can also use the additional capabilities provided by the browser.

console.log("Start");

setTimeout(() => {
    console.log("Timer finished");
}, 2000);

console.log("End");

Output:

Start
End
Timer finished

Here, setTimeout() is not core JavaScript syntax. It is a timer API provided by the runtime environment. The browser manages the timer while JavaScript continues executing the next statement.

2. What Are Web APIs?

Web APIs are capabilities exposed by the browser that JavaScript code can use. They let web applications interact with timers, web pages, network requests, user events and other browser features.

Timer API
setTimeout(), setInterval()

Schedule a callback to run after a delay or repeatedly at intervals.

Network API
fetch()

Make HTTP requests and handle responses from servers.

DOM APIs
document, event listeners

Access and update web page elements and respond to user interactions.

Other Browser APIs
Examples include storage, notifications and geolocation APIs.

Provide access to additional browser capabilities, subject to permissions where required.

Important: Not every Web API is asynchronous. For example, many DOM property accesses are synchronous. Web APIs include both synchronous and asynchronous functionality.

3. How Does the Browser Expose These APIs to JavaScript?

When a browser runs JavaScript in a web page, it provides a global environment with access to browser APIs. That's why you can call setTimeout() without importing it.

For example, in a browser:

console.log(typeof setTimeout);        // "function"
console.log(typeof window.setTimeout); // "function"

window.setTimeout(() => {
    console.log("Hello");
}, 1000);

You don't need a separate JavaScript import for these built-in browser APIs. The browser exposes them through the environment in which your code runs.

↓

↓
JavaScript calls the API
↓
Browser manages the timer
↓
Callback becomes eligible to run
↓
Event loop coordinates when the callback executes

JavaScript doesn't run only in browsers. Node.js can also execute JavaScript, but it provides a different runtime environment.

setTimeout() works in Node.js too. That doesn't mean Node.js is running a browser. Node.js provides its own timer APIs and other capabilities, such as filesystem access.

Callback Task Queue or Macrotask queue — Where Does a Callback Wait?

நாம் ஏற்கெனவே புரிந்துகொண்டது:

  • Browser timer-ஐ schedule செய்கிறது.
  • Timer முடிந்ததும், callback execute செய்யத் தயாராகிறது.
  • JavaScript main thread ஏற்கெனவே synchronous code-ஐ execute செய்துகொண்டிருந்தால், callback அதை இடைமறித்து run ஆக முடியாது.

Question: Execute செய்யத் தயாராக இருக்கும் callback எங்கே காத்திருக்கும்?

Answer: Callback Task Queue-ல் காத்திருக்கலாம்.

Callback தனது turn-க்காகக் காத்திருக்கிறது
↓ Callback execute ஆகிறது

Remember:

Callback Queue என்பது தனியாக ஒரு thread அல்ல; அது waiting callbacks-க்கான queue.

Microtask Queue vs Callback Task Queue

Macro - BIG, Micro - small

நாம் ஏற்கெனவே கற்றுக்கொண்டது: Timer முடிந்த பிறகு அதன் callback execute ஆகத் தயாராகி Task Queue-ல் காத்திருக்கும். ஆனால் எல்லா asynchronous callbacks-உம் ஒரே queue-ல் காத்திருப்பதில்லை.

JavaScript runtime-ல் இரண்டு முக்கியமான scheduling mechanisms உள்ளன:

1. Callback Task Queue

Ordinary Tasks

  • setTimeout()
  • setInterval()
  • Many DOM event callbacks
  • Other browser tasks

Task execute செய்யத் தயாரான பிறகு தனது turn-க்காகக் காத்திருக்கும்.

2. Microtask Queue

Microtasks

  • Promise.then()
  • Promise.catch()
  • Promise.finally()
  • queueMicrotask()

Microtask checkpoint-இல் execute செய்யப்படுவதற்காகக் காத்திருக்கும்.

Important: Microtask Queue என்பது Task Queue-ஐ விட முன்னுரிமையாக process செய்யப்படும் தனி queue. இது ஒரே queue-ல் priority கொடுப்பது போன்றது அல்ல; இரண்டும் தனித்தனியான scheduling mechanisms.

1. How Does the Browser Process These Queues?

Current JavaScript task முடிந்ததும், browser microtask checkpoint-ஐச் செய்கிறது. அதாவது, Microtask Queue-ல் இருக்கும் microtasks அனைத்தும் empty ஆகும் வரை ஒவ்வொன்றாக execute செய்யப்படும். அதன் பிறகு browser அடுத்த task-ஐ process செய்யலாம்; rendering-க்கும் வாய்ப்பு கிடைக்கலாம்.

Current JavaScript Task finishes
↓
Microtask Queue
↓
Process microtasks until EMPTY
↓
Rendering opportunity (when applicable)
↓
Next Task from a Task Queue
↓
Next Microtask Checkpoint
Remember: Microtasks are processed before the event loop moves on to another task. If a microtask adds another microtask, that new microtask is also processed in the same checkpoint.

2. First Example — Promise vs setTimeout vs queueMicrotask

console.log("Start");

setTimeout(() => {
    console.log("Timer callback");
}, 0);

Promise.resolve().then(() => {
    console.log("Promise microtask");
});

queueMicrotask(() => {
    console.log("Direct microtask");
});

console.log("End");
Final Output
Start
End
Promise microtask
Direct microtask
Timer callback
Why This Output?

Let's follow the execution order:

Step Operation Where It Goes
1 console.log("Start") Executes immediately
2 setTimeout() Schedules a Timer Task
3 Promise.then() Microtask Queue
4 queueMicrotask() Microtask Queue
5 console.log("End") Executes immediately
6 Microtask checkpoint Promise callback, then Direct microtask
7 Timer Task Timer callback executes later

Why does Promise execute before setTimeout? Because Promise callbacks are microtasks, and microtasks are drained before the next ordinary task is processed.

Why does Promise microtask execute before Direct microtask? Both are added to the Microtask Queue in that order. The queue follows FIFO (First In, First Out) ordering.

Note: setTimeout(..., 0) does not mean the callback runs immediately. It becomes eligible after the timer delay and runs when the event loop gets to its task. Here, the microtasks run first.

3. FIFO — What Happens When One Microtask Adds Another?

Let's understand an interesting case: a microtask can schedule another microtask while the queue is already being processed.

console.log("Start");

queueMicrotask(() => {
    console.log("M1 - A");

    queueMicrotask(() => {
        console.log("M2");
    });

    console.log("M1 - B");
});

queueMicrotask(() => {
    console.log("M3");
});

console.log("End");
Final Output
Start
End
M1 - A
M1 - B
M3
M2
Understand the Queue Step by Step

Before microtask processing begins, the first two microtasks are already queued.

Initial Microtask Queue
┌──────────┐
│ M1 │
│ M3 │
└──────────┘
Step What Happens Remaining Queue
1 M1 starts and prints M1 - A. M3
2 M1 schedules M2 at the end of the queue. M3 → M2
3 M1 prints M1 - B and finishes. M3 → M2
4 M3 executes. M2
5 M2 executes. Empty
Important: M2 does not jump ahead of M3. It is added to the end of the Microtask Queue, so M3 executes first.

4. Task Queue vs Microtask Queue — Quick Comparison

Also called Callback Queue / Macrotask Queue (informal terms) Microtask Queue

Technical note: "Macrotask Queue" and "Callback Queue" are commonly used learning terms. Browser standards describe multiple task queues/task sources rather than one single universal FIFO queue for all tasks. The Microtask Queue is a separate scheduling mechanism.

5. Microtask Starvation

We know that the browser processes microtasks until the Microtask Queue becomes empty.

But what happens when microtasks continuously add more microtasks?

This can cause a problem called Microtask Starvation.

Example: Scheduling Microtasks Repeatedly
console.log("Start");

let count = 1;

function repeatMicrotask() {
    console.log("Microtask", count);

    if (count < 3) {
        count++;
        queueMicrotask(repeatMicrotask);
    }
}

setTimeout(() => {
    console.log("Timer");
}, 0);

queueMicrotask(repeatMicrotask);

console.log("End");
Final Output
Start
End
Microtask 1
Microtask 2
Microtask 3
Timer

Why does the Timer execute last?

  1. The timer callback is scheduled as a task.
  2. repeatMicrotask is added to the Microtask Queue.
  3. The current JavaScript task finishes, and the microtask checkpoint begins.
  4. Microtask 1 schedules Microtask 2.
  5. Microtask 2 schedules Microtask 3.
  6. The queue becomes empty only after Microtask 3 finishes.
  7. Now the event loop can move on to the Timer task.

6. What If We Remove the Condition?

Imagine removing this condition:

if (count < 3) {
    count++;
    queueMicrotask(repeatMicrotask);
}

And always scheduling another microtask:

function repeatMicrotask() {
    console.log("Microtask", count++);
    queueMicrotask(repeatMicrotask);
}

Now each microtask schedules another microtask forever. The Microtask Queue never becomes empty.

Microtask Starvation

When microtasks continuously schedule more microtasks, the browser may never get an opportunity to process the next task or update the page.

This can:

  • Delay timer callbacks.
  • Delay browser rendering and UI updates.
  • Make a webpage appear frozen or unresponsive.

Why is this dangerous? The browser drains microtasks before moving on to another task. If that drain never finishes, other work cannot get its normal turn.

  2. Timer callbacks and many DOM event callbacks are tasks.
  3. Promise callbacks and queueMicrotask() callbacks are microtasks.
  4. Microtasks are drained before the event loop moves to the next task.
  5. Continuously scheduling microtasks can cause Microtask Starvation.

Event Loop — How JavaScript Handles Asynchronous Execution

The Event Loop is not a queue, and it is not another JavaScript thread. It is part of the runtime's execution-scheduling mechanism. It coordinates when queued tasks and microtasks can execute.

JavaScript executes the current task (synchronous) to completion, processes pending microtasks at the microtask queue, and then the browser can proceed to another ordinary task(callback queue or macrotask queue).

We have already learned about the Call Stack, Web APIs, Task Queue and Microtask Queue. Now let's understand how they work together.

Callback Hell — Understanding Nested Callbacks

1. First, Why Were Callbacks Introduced?

Callbacks allow us to execute a function after an asynchronous operation finishes and provide its result to another function.

function getUser(callback) {
    setTimeout(() => {
        const user = {
            id: 101,
            name: "John"
        };

        callback(user);
    }, 1000);
}

getUser((user) => {
    console.log(user);
});
How Does It Work?
1. getUser() starts an asynchronous operation
↓
2. Timer finishes after approximately 1 second
↓
3. callback(user) executes the function we passed
↓
4. User information is printed

Here, callback(user) invokes the callback function and passes the user object as an argument.

Remember: Callbacks are useful for handling the results of asynchronous operations.

2. Now Imagine Multiple Dependent API Calls

Suppose we are developing an e-commerce application. We need to retrieve information through multiple API calls.

Each operation depends on the result of the previous operation.

1. Get User
User ID

Retrieve user information.

2. Get Orders
User ID

Retrieve the user's orders.

3. Order Details
Order ID

Retrieve order information.

4. Shipping Details
Address ID

Retrieve shipping information.

5. Display Result
Final Data

Display order and shipping details.

Get User
↓ user.id
Get Orders
↓ orders[0].id
Get Order Details
↓ orderDetails.addressId
Get Shipping Details
↓
Display Final Result

Notice: Each API call needs data from the previous API call. Therefore, we need to wait for one result before starting the next dependent operation.

3. What Exactly Is Callback Hell?

When multiple asynchronous operations depend on each other, we may end up placing callbacks inside other callbacks, creating deeply nested code.

Let's look at the same e-commerce workflow using nested callbacks.

getUser(101, function(user) {

    getOrders(user.id, function(orders) {

        getOrderDetails(orders[0].id, function(orderDetails) {

            getShippingDetails(orderDetails.addressId, function(shipping) {

                console.log(user);
                console.log(orders);
                console.log(orderDetails);
                console.log(shipping);

            });

        });

    });

});

Here, assume each function performs an asynchronous operation and invokes its callback when the result is ready.

Look at the Structure
getUser()
└── getOrders()
    └── getOrderDetails()
        └── getShippingDetails()
            └── Display Result

Every callback is nested inside the previous callback. As more dependent operations are added, the code moves further and further to the right.

This structure is commonly called:
  • Callback Hell
  • Pyramid of Doom

4. Why Is Callback Hell a Problem?

Deep Nesting

Too many nested callbacks make the code difficult to follow.

Readability

Understanding the execution flow becomes harder.

Error Handling

Each asynchronous operation may need separate error handling.

Maintenance

Changing or debugging deeply nested code becomes more difficult.

5. Important: Callbacks Are Not Bad

Callbacks are still useful and widely used in JavaScript. The problem is not callbacks themselves; it is excessive nesting of dependent asynchronous callbacks.

Final Takeaway

Callback = A function passed to another function to be executed later or at a particular point.

Callback Hell = Deeply nested callbacks that make asynchronous code difficult to read, maintain and handle errors in.
